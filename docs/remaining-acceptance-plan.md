# S11 剩余阻塞项验收施工清单

更新日期：2026-09-23。范围：现有 OPT-350M 完整推理的正式验收，以及已知
SDK/内存问题的独立复测。不增加 TLM、投机协议、完整 Qwen 推理或新的优化框架。

## 施工顺序与依赖

| 顺序 | 工作 | 依赖 | 完成条件 |
|---|---|---|---|
| S11.1 | 分开测量分配容量与全区段读回（已完成本次诊断） | 当前设备可用；已有容量工具 | 完整分配记录、异常区段表、正常释放证据；不等同于修复 |
| S11.2 | 定位并修正每 token 主机分配增长 | 短序列数值基线；HAL 计数语义/分配栈支持 | 找到分配来源，修复后同一模型长期复用时分配有界 |
| S11.3 | 建立 kernel 执行与物理内存观察方法 | 芯片团队提供可用工具/说明 | 已知小图对照证明工具有效，能关联 kernel、设备、分配与传输 |
| S11.4 | 验收完整模型与 KV 驻留、释放 | S11.3；S11.2 修复后做最终复测 | 完整算子路径、物理内存预算、状态驻留及释放证据齐全 |
| S11.5 | 长上下文、持续运行及性能验收 | S11.2、S11.4；当前 OPT 数据路径正确 | 边界数值、长期资源稳定、无跟踪性能报告均通过 |
| 独立支线 | 修复大容量数据损坏、卷积异常、直接 FP16 采样 | 各自的最小复现和研发团队答复 | 按下述专项判据关闭对应 TODO |

S11.2 的本地定位与 S11.3 的研发团队沟通可以同时推进。
大容量损坏不自动否定当前较小 OPT 配置的数值结果，但未通过验证的容量不能
用于部署预算；如果它影响 S11.4/S11.5 的实际配置，则成为该配置的硬阻塞。
卷积问题不阻塞当前已经通过数值验证的 OPT 路径。

## S11.1：容量与损坏区段（本次工作）

- [x] FP16/FP32、constant/mutable 分别执行小容量对照。
- [x] 使用 `check_np101_capacity.py --readback none --target-mib 4096`，以 8 MiB
  块逐步保留张量，直到 SDK 拒绝或到达目标；记录拒绝阶段和错误。
- [x] 在可保留的大容量上使用 `--readback all`，比较全部块，遇到字节不匹配
  继续扫描；SDK 调用失败、信号、超时或释放失败则停止。
- [x] 输出每块实际检查范围、不匹配字节数、连续区间和逻辑 4 KiB 页覆盖范围；
  保留第一个损坏块的 expected/actual 原始字节。
- [x] 对照不同 dtype/storage 的异常位置；必要时只重复一个配置确认复现性。
- [x] 将结果写入 [容量记录](../tests/np101-capacity.md) 和 `NP101-MEM-001`。

本次四种组合均在保留 2,840 MiB 后拒绝下一块 8 MiB；所有大容量扫描均只发现
第 109 块中相同的 24 字节异常。范围和原始记录见上述容量文档。S11.1 完成的是
诊断交付，大容量数据正确性问题仍待厂商修复或提供有依据的解释。

所有区间使用从零开始、右端不包含的偏移。累计 payload 偏移不是物理地址，
不据此建立“坏物理页”黑名单。达到 4 GiB 只表示本次测试下限，不能凭空推断
真实极限；SDK 拒绝也只形成该块大小/分配路径下的边界。分配通过不关闭数据正确性问题。

## S11.2：每 token 主机内存增长（NP101-MEM-003）

施工位置：优先复用 `tests/native/np101/kv_cache_check.cpp`、
`native/np101/kv_cache.cpp` 和现有短序列验收 runner；定位探针先放 `.cache/runs/`，
只有最终回归需要的检查才进入常驻测试。

1. 固定 SDK、checkpoint、capacity 和 token 序列；留存当前正确输出与计数基线。
2. 将一次 KV 更新分为设置图参数、`vxVerifyGraph`、`vxProcessGraph` 三段，
   在段外采样 HAL 主机分配计数；先确认开启采样后输出结构确实被 SDK 写入。
3. 先测试单层、小容量 KV，比较“重复写同一槽”和“逐槽追加”两种固定规模实验；
   记录各段分配增量和验证次数，确认是否真的与每 token 的 48 次分配有关。
4. 分别记录图、张量引用、context 释放前后，以及 SDK 退出时计数；必要时请研发
   提供分配调用栈/内部对象寿命信息。不能仅凭 RSS 不下降就认定泄漏。
5. 根据证据修复应用所有权或使用厂商修正；如要调整 KV 图绑定，先验证原地追加、
   前缀不变、边界和引用寿命。不改成整段缓存复制或完整 KV 双缓冲。
6. 对修复后的单层 KV 做至少两轮容量循环，再做完整 OPT 同实例预热后 20 次
   短请求、两次新进程生命周期；比较 CPU token 和显式传输总量。

验收：预热之后没有随请求/token 数线性增长的未解释存活分配；已知缓存必须给出
有限上界，并由超过该上界对应循环次数的测试证明进入平台。模型/context/SDK
关闭后的残留符合厂商说明，无残留设备进程。若计数语义仍不清楚，保持阻塞。

交付：最小复现、分阶段计数、根因与修复、一个必要的资源稳定性回归。完成前不
执行完整模型长上下文/压力验收；短数值检查可继续。

## S11.3：执行与物理内存观测（NP101-OBS-001）

向芯片团队索取并实际验证：

1. 当前 1.0.6 配套工具及开启/关闭命令；每条 kernel 的标识、实际执行引擎、
   开始/完成事件，以及软件回退的明确识别方法。
2. tensor/分配与板载物理池的关联、分配/释放/峰值事件、内部布局副本与 workspace
   的统计口径；解释现有 `gpu_memory` 对 8 MiB 张量统计约 16 MiB 的原因。
3. DMA/host-device 传输的方向、字节数和对象关联，能够区分用户上传、SDK 内部复制
   与设备内复制；说明工具本身是否改变执行路径。

施工：先用小张量分配/释放对照标定内存观察，再用已验证的极小 MatMul/Add 图确认
执行引擎关联。如果工具支持软件模式，再加入厂商支持的软件对照；不自行猜测开关。
随后把可重复的证据采集入口接到现有 runner，并记录工具版本和设置。

验收：能根据事件回答“哪个 kernel 在哪里完成、哪个 tensor 占用哪个池、何时释放”。
目标名称、普通 ioctl、SDK 返回成功、数值匹配、壁钟时间均不单独作为这一项证据。
取得工具前可整理接口和归档格式，但不设置 `hardware_execution_proven=true`。

## S11.4：完整模型与状态驻留（NP101-OBS-001 / STATE-001）

1. 固定 OPT-350M、24 层、FP16 原始权重和 checkpoint 默认生成策略。
2. 带诊断跟踪执行现有 selection、teacher、两条 prompt 的短生成；关联 embedding、
   24 个 decoder、KV 写入、最终归一化/投影/LM head/选 token 的所有实际 kernel。
3. 区分首次初始化/布局转换、prefill、decode、reset 四个阶段；核对权重和 KV 的
   物理驻留。确认逐 token 不经主机搬运权重、完整 KV 或隐藏状态。
4. 统计 unique weights、KV、激活、布局副本、workspace、预留区及物理峰值；以同一
   时刻实际存活分配求和，不能直接把不同阶段峰值相加。
5. 同实例 reset/reuse、销毁重建、新进程分别验证数据与物理资源释放。

应用层预期仍是每 consumed token 上传 104 字节控制量、每次预测读回 4 字节 ID、
每 consumed token 24 次 KV 追加；这些计数只检查应用，必须另有 SDK 内部传输证据。

验收：完整计算路径满足既定板卡执行目标，状态无逐 token 主机回传；驻留预算有
可复核的余量，释放观察闭合。若出现 CPU/软件回退，明确列出算子和原因并保持阻塞。
这些诊断运行不计入性能报告。

## S11.5：边界、持续运行和性能

1. 容量从 32、128 到 512 逐级验证；每级通过后再前进。固定 token ID 的 teacher
   序列覆盖早期、中部、最后槽位和容量耗尽，检查原位追加、reset 后前缀及越界拒绝。
2. 用真实 prompt 做短/中/长 prefill 和多步生成，与固定版本官方 CPU 实现比较；
   遇到首个 token 分歧再导出该步必要中间值，不在测量路径启用全量读回。
3. 默认策略下逐 token 应精确匹配；若出现边界 logits 数值差异，先保留误差和排序
   证据，单独审阅判据，不为了通过验收临时放宽阈值。
4. 使用 S11.2 的稳定性方法检查同实例连续请求与重建。记录 RSS、已解释的 SDK
   存活分配、物理峰值；压力规模受已验证预算约束。
5. 关闭 strace、SDK profiler 和额外读回，以相同配置独立测量：至少一次预热、
   每条 prompt 三次测量、两次新进程初始化。记录初始化、prefill、首 token、
   decode、吞吐、样本数/分布及实际上下文长度。

验收：数值、状态、资源稳定性、执行与驻留全部通过后，才发布正式性能结果。
性能验收首先保证测量有效、可重复且没有未解释退化；具体速度指标需另行制定，
不能把当前约 0.62 token/s 的短测试观测直接设为达标目标。

## 统一交付和停止条件

- 每次运行使用独立输出目录，保存可执行文件、源码/SDK hash、boot ID、参数、
  原始日志、CPU 参考和结构化判断；失败数据不混入成功性能样本。
- 纯容量诊断可以按本次要求忽略**字节不匹配**继续扫描。首次分配/初始化拒绝
  终止申请，随后检查已成功保留的块；读回 API 失败、进程信号、超时、释放失败
  或恢复标记则停止后续设备实验。正常释放后才运行下一项。
- 只保留能防止实际回归的单元测试和设备检查，沿用现有目录和 runner，不引入新测试框架。
- 每项单独更新 `TODO.md` 与对应 `tests/np101-*.md`，记录通过、阻塞、依赖和证据路径。
  生产实现的行为变更与纯观测工具分开审阅。
