## S11.2：每 token 主机内存增长（NP101-MEM-003）

施工位置：优先复用 `tests/native/np101/kv_cache_check.cpp`、
`native/np101/kv_cache.cpp` 和现有短序列验收 runner；定位探针先放 `.cache/runs/`，
最终保留两个独立运行的 native 内存诊断，复用现有资源管理；大容量读回复用
capacity 工具。入口与记录见 [内存诊断](../tests/np101-memory.md)。

1. 固定 SDK、配置和 token 序列，沿用已观察到的每 consumed token 约 3 MiB
   RSS 增长及既有 HAL 日志。当前不重新启用内存或 kernel profiler。
2. 单层、小容量 KV 分别执行重复写同一槽、逐槽追加、重复经过相同槽位；
   在参数绑定、图验证、执行与释放阶段的边界记录进程 RSS、调用次数和耗时。
   用少量重复观察趋势；RSS 不能精确归因到分配调用，不据此宣告根因。
3. 核查应用引用寿命和容器大小是否固定。视图目前在初始化时一次创建，重点
   对照逐 token 的 `vxVerifyGraph` 次数与增长；不预设二者存在因果关系。
4. 若证据指向 SDK 且现有观察无法继续区分，提交最小复现与旧 HAL 日志，
   标记待厂商定位；不为等待答复阻断有界的短请求检查。
5. 如能局部修复，复测相同槽位循环、KV 数值、reset 与释放。不得以完整缓存复制
   或完整双缓冲替换当前追加方案，也不得仅绕过必要的图验证来隐藏问题。

本轮交付：最小复现或更明确的排除结果、按 consumed token 归一化的增长记录、
对短请求测试规模的约束。短序列重复请求每个进程保持不超过 256 个 consumed token。按用户要求，
较长输入单独使用新进程、零预热和一次测量；运行前按每 consumed token 4 MiB
加 4 GiB 余量检查主机可用内存，2048 步至少要求约 12 GiB 可用。
记录实际 RSS；增长超出预算则停止，不把这个估算作为内存上界证明。

关闭 MEM-003 仍需要解释/修正增长并验证预热后分配有界。仅进程退出释放主机
地址空间不能算修复。同实例 20 次请求和长期稳定性留到根因修复后的专项验收，
不是本轮有界功能与计时的前置条件。

## S11.3：执行与物理内存观测（低优先级，当前暂缓）

恢复该项目时，验证厂商提供的工具和说明：

1. 当前 1.0.6 配套工具及开启/关闭命令；每条 kernel 的标识、实际执行引擎、
   开始/完成事件，以及软件回退的明确识别方法。
2. tensor/分配与板载物理池的关联、分配/释放/峰值事件、内部布局副本与 workspace
   的统计口径；解释现有 `gpu_memory` 对 8 MiB 张量统计约 16 MiB 的原因。
3. DMA/host-device 传输的方向、字节数和对象关联，能够区分用户上传、SDK 内部复制
   与设备内复制；说明工具本身是否改变执行路径。

施工：先用小张量分配/释放对照标定内存观察，再用已验证的极小 MatMul/Add 图确认
执行引擎关联。如果工具支持软件模式，再加入厂商支持的软件对照；不自行猜测开关。
随后把可重复的证据采集入口接到现有 runner，并记录工具版本和设置。

验收：能根据事件回答“哪个 kernel 在哪里完成、哪个 tensor 占用哪个池、何时释放”。
目标名称、普通 ioctl、SDK 返回成功、数值匹配、壁钟时间均不单独作为这一项证据。
暂缓期间保留 `hardware_execution_proven=false`。完整模型的权重/KV 物理驻留、
SDK 内部搬运、布局/workspace 峰值和物理释放证明也归入本项；当前功能验收
不得声称已完成这些检查。此项不作为功能与壁钟测量的前置条件。单张量内存计数复现可在独立进程
启用内存统计，不属于推理 profiler 验收，不混入性能样本。

## S11.4：KV 功能与完整短序列生成（本轮主线）

配置：OPT-350M、全部 24 层、原始 FP16 权重、checkpoint 默认 greedy 策略、
batch size 1。常规检查固定 capacity 64；小容量边界单独用 capacity 8。

1. **共享 KV 存储。** 复用 `tests/native/np101/kv_cache_check.cpp`，传入 OPT 的
   heads/head_dim 与短容量；检查首槽、相邻槽、末槽和覆写。新槽字节正确，历史
   槽不变，固定 reader 不经缓存主机读回即可观察更新。保留最终一次读回路径
   和越界提交前拒绝检查；不再新增同功能 runner。
2. **真实模型中的 KV。** 复用 OPT decoder 和完整模型 teacher 检查。在 prefill
   结束、首个 decode consume 后、短序列末尾记录全部层的有效 KV 前缀，按已有
   精度策略与独立 CPU cache 对比；有效长度、追加次数和历史前缀分别检查。
   仅诊断运行允许这些读回，正式生成继续直接使用同一份缓存。
3. **重置与污染隔离。** 用不同长度/内容的 A、B prompt 在同一模型实例执行
   A → reset → B → reset → A。两次 A 及 B 分别与全新 CPU 状态比较，检查旧后缀
   不参与 Attention。现有 benchmark 只重复同一 prompt，此处需补最小的多请求
   驱动能力；复用生产 `Model::generate`，不实现另一套生成逻辑。
4. **完整 response。** 选择约 8、16、32 token 的三条英文续写 prompt（以实际
   tokenizer 计数为准），最多生成 16 个 token，遵守 EOS。保存 prompt/token IDs、
   每步预测、解码文本、停止原因，与官方 CPU 生成逐 token 精确比较。
   OPT-350M 的文本能力单独观察，不用主观回答质量替代正确性判据。
5. **小容量边界与生命周期。** capacity 8 验证最后有效槽、超限拒绝、reset、
   prompt 刚好填满容量仍可预测一次；同实例复用和两个新进程正常释放。
   记录 consumed tokens，最后一个已预测但未继续消费的 token 不应计入 KV。
6. **保留传输约束。** 正常生成每 consumed token 104 字节应用控制上传、24 次
   KV 追加，每次预测读回 4 字节 ID；无应用层完整 KV/隐藏状态/权重逐步回传。
   SDK 内部行为仍待 S11.3，不从这些应用计数推断物理驻留。

施工文件：沿用 `native/cli/opt_generate.cpp`、`scripts/check_np101_acceptance.py`、
`python/specferry/models/opt/acceptance.py` 与现有 OPT decoder/generation 检查。
先核对现有覆盖，再补检查点、多请求输入与报告，避免再造一套测试。
单元回归只覆盖新增语义：A/B/A 污染、KV 有效长度/比较失败、边界计数和报告分级。

验收：上述短序列的 KV、CPU 数值/token、输出解码、停止和应用生命周期检查全部
通过。发生分歧先定位，不为通过临时放宽阈值。短期通过不关闭 MEM-003，
不等同于物理驻留或长期稳定性已证明。

## S11.5：短上下文性能基线

1. 短序列重复测量使用 32 token 自然文本前缀、capacity 64、最多 16 个新 token。
   新增 128/512/2048 token 输入，各使用一个新进程、零预热、一次测量；
   capacity 根据输入与输出空间计算，最多 2048。OPT 的 learned positions 上限
   为 2048，满长度输入只能再预测一次，decode tokens/s 必须为 null；
   另测 2033 token 输入，保留 16 次预测空间以观察接近上限时的连续输出。
   当前 prefill 是逐 token consume，报告明确这一实现，不混同批量 prefill。
2. 32 token 的短输入基线在两个新进程分别加载模型；每进程一次预热、三次测量并复用模型。
   含预热的 consumed token 总数保持在 S11.2 的预算内；EOS 提前结束按实际数计。
3. 使用现有 native benchmark。CPU 参考在测量前准备；测量时关闭 strace、profiler、
   逐 token 打印与诊断张量读回。每轮输出仍须与 CPU 比较，失败则停止，不选取
   失败轮次中的部分 token 作为成功性能数据。
4. 保存解码文本与精确 tokenizer 输入长度。使用连续自然语言故事，按 token
   截取前缀；不随机填充，不重复同一段落凑长度。边界截断可落在句中或子词中。
   生成文本供人工观察，正确性仍以相同 checkpoint CPU 结果为准。
5. 保留每次请求原始计时、实际 prompt/output/consumed 数、停止原因、预热与
   测量标记、初始化时间和请求间 RSS。报告中位数及范围、样本数；少量样本的
   p95 仅保留为观察值，不给出稳定尾延迟结论。

| 指标 | 统一口径 |
|---|---|
| 初始化 | context 与完整模型构建；已有权重文件校验另列，不包含在该计时中 |
| Prefill 时间/吞吐 | 消费全部 prompt IDs 至首次 head 调用之前；prompt token 数 / prefill 时间 |
| 模型就绪 TTFT | reset 完成且 token IDs 就绪后，至第一个预测 ID 返回；包含 prefill 和首次 head/读回 |
| TPOT / decode 吞吐 | 首 token 之后的相邻输出间隔；汇总为 decode 总耗时 / 间隔数及其倒数 |
| 请求总耗时 | reset 后开始 prefill 至生成完成；不含模型初始化、tokenization、网络、文本显示 |
| 主机资源 | 每轮前后 RSS、峰值、每 consumed token 增长；不当作板载物理内存 |

生成 N 个 token 只有 N−1 个 decode 间隔；N=1 时 decode 吞吐为 null。
TTFT 与初始化分别展示，不把当前时间命名为端到端服务 TTFT。

施工同时调整验收报告：短请求功能、计时有效性、已知资源问题和暂缓事项分开列出；
默认严格硬件验收仍保留 pending，显式功能/diagnostic 模式可返回成功。不得通过
删除原始证据或将硬件 flags 改为 true 来获得通过。CLI、文档与报告字段同步。

验收：短上下文功能通过，得到可复现的**当前 SDK 推理路径主机壁钟性能**及其
资源变化。不要求先完成 S11.3 或长期稳定性；已知增长必须披露，不能声称稳态。
不设未讨论过的速度门槛，旧记录约 0.62 token/s 仅作历史对照。

## 统一交付和停止条件

- 每次运行使用独立输出目录，保存可执行文件、源码/SDK hash、boot ID、参数、
  原始日志、CPU 参考和结构化判断；失败数据不混入成功性能样本。
- 纯容量诊断可以按本次要求忽略**字节不匹配**继续扫描。首次分配/初始化拒绝
  终止申请，随后检查已成功保留的块；读回 API 失败、进程信号、超时、释放失败
  或恢复标记则停止后续设备实验。正常释放后才运行下一项。
- 只保留能防止实际回归的单元测试和设备检查，沿用现有目录和 runner，不引入新测试框架。
- 每项单独更新 `TODO.md` 与对应 `tests/np101-*.md`，记录通过、阻塞、依赖和证据路径。
  生产实现的行为变更与纯观测工具分开审阅。
